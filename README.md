# Оформление билетов

Сервис покупки билетов на мероприятие (моковые данные: одно событие, 12 мест).
Стек: FastAPI, asyncio, SQLAlchemy 2 (async), Pydantic, PostgreSQL, Alembic, Redis, React + Vite + TypeScript.

## Настройка: .env

Данные подключения к БД лежат в `.env` в корне проекта. Шаблон — `.env.example`:

```bash
cp .env.example .env     # если .env ещё нет; файл в .gitignore и в репозиторий не попадает
```

| Переменная | Для чего |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | создают БД в контейнере `db` и используются backend для подключения |
| `POSTGRES_HOST`, `POSTGRES_PORT` | адрес БД при запуске backend **без** Docker; порт — ещё и внешний порт контейнера `db` |
| `DATABASE_URL` | необязательно: готовая строка подключения вместо частей выше |

В Docker backend подключается к хосту `db` (compose подменяет `POSTGRES_HOST`), остальное берёт из `.env`.
Переменные, уже заданные в окружении, приоритетнее файла. Если обязательная переменная не задана,
backend остановится с понятным сообщением. Пароль можно писать как есть: строка подключения собирается кодом и экранирует спецсимволы.

Если меняете логин, пароль или имя БД после первого запуска, удалите том со старыми данными:
`docker compose down -v` (Postgres применяет эти значения только при создании БД).

## Запуск

```bash
docker compose up --build
```

Откройте http://localhost:8080 (документация API: http://localhost:8000/docs).
Миграции и демо-событие применяются автоматически при старте backend.

Без Docker (БД можно поднять только контейнером: `docker compose up -d db redis`):

```bash
# backend (Redis по желанию — без REDIS_URL всё работает)
cd backend
pip install -r requirements.txt
export ENABLE_DEV_ENDPOINTS=1     # демо-ручка; подключение к БД берётся из ../.env
alembic upgrade head
uvicorn app.main:app --reload

# frontend (Vite проксирует /api на :8000; демо-кнопки видны в dev-режиме)
cd frontend
npm install
npm run dev        # с телефона: http://<IP-компьютера>:5173
```

## Тесты

```bash
# backend: правила заказа (без БД)
cd backend && pip install -r requirements-dev.txt && pytest

# backend: + API и конкурентность на реальной PostgreSQL (после alembic upgrade head)
RUN_DB_TESTS=1 pytest

# e2e в браузере (проект должен быть поднят через docker compose)
cd frontend && npm install && npx playwright install chromium && npm run test:e2e
```

E2E гоняются в двух вьюпортах: телефон 360 px и десктоп. Каждый прогон записывается на видео в
`frontend/test-results/` — это можно приложить как видеозапись процесса. CI (`.github/workflows/ci.yml`)
выполняет оба набора тестов.

## Правила и допущения

- От 14 лет — 2 000 ₽, младше 14 — 1 000 ₽. Участников в заказе от 1 до 4.
- «Ребёнок» = младше 14 лет (детский билет): ему нужен хотя бы один участник от 18 лет в том же заказе.
  Подросток 14–17 лет платит полную цену и может прийти без взрослого — это моё прочтение условия.
  Пороги, цены и лимиты — в одном файле `backend/app/domain/pricing.py`.
- Фронтенд получает правила вместе с событием (`GET /api/events/{id}`) и цены не считает: итог всегда приходит от сервера.
- Оплаты и отправки писем нет: это моковый сценарий.

```
                   │

```

### Бронь мест

- «Проверить заказ» (`POST /api/holds`) валидирует данные и закрепляет места на `HOLD_TTL_SECONDS` (по умолчанию 600 с). Клиент показывает обратный отсчёт; время считается по `ttl_seconds` из ответа, а не по сравнению часов клиента и сервера.
- Свободно = `capacity − sold − сумма активных броней`. Чужие брони уменьшают то, что видят новые покупатели.
- Инвариант `capacity >= sold + активные брони` держит блокировка строки события (`SELECT … FOR UPDATE`): создание брони и подтверждение заказа по одному событию идут по очереди. Дополнительно в БД стоит `CHECK (sold <= capacity)`.
- Повторное «Проверить заказ» после правок передаёт `replace_hold_id`: прежняя бронь освобождается в той же транзакции. Если мест на новый состав не хватает, транзакция откатывается и старая бронь остаётся.
- «Подтвердить» (`POST /api/orders`) в одной транзакции удаляет бронь покупателя, пересчитывает свободные места, списывает их и создаёт заказ. Истёкшая бронь не мешает: места добираются заново, а если их не осталось — `409 SOLD_OUT`.
- Брони хранятся в PostgreSQL, а не в Redis: так бронь и продажа меняются в одной транзакции, и не нужно согласовывать два хранилища. Истёкшие брони чистит фоновая задача (`asyncio`, раз в минуту), но для подсчёта они и так не учитываются.

### API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/events/{id}` | событие, правила, свободные места (с учётом броней) |
| POST | `/api/orders/quote` | проверка и расчёт без записи и без брони |
| POST | `/api/holds` | проверка + бронь мест: `201`, `422 VALIDATION`, `409 SOLD_OUT` |
| POST | `/api/orders` | подтверждение (`Idempotency-Key`, `hold_id`): `201`, `422`, `409 SOLD_OUT` |
| GET | `/api/orders/{id}` | заказ (экран успеха после перезагрузки) |
| POST | `/api/dev/events/{id}/seats?left=N` | только демо/e2e: сбросить брони и оставить N мест |

Ошибки машиночитаемы: `422 {"code":"VALIDATION","errors":[{"field":"participants[0].age","code":"AGE_REQUIRED","message":"…"}]}`
и `409 {"code":"SOLD_OUT","seats_left":N,"requested":K}` — клиент привязывает их к полям.

Повтор подтверждения безопасен: заголовок `Idempotency-Key` + уникальный ключ в БД (Redis лишь быстрее отсекает параллельный дубль).
